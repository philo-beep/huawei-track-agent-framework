## 一、本轮已修正的询问方式与称呼

### 1. 使用者定位

本项目使用者是**华为销售顾问**。画像访谈的输入是销售顾问录入的客户原话、转述或销售观察，不是终端客户直接与聊天机器人对话。

### 2. 已修正内容

- 画像维度统一使用客户本位名称：客户角色、客户行业、客户使用场景、客户需求、客户痛点、客户采购阶段、客户预算、客户沟通偏好、客户方案认知、客户偏好。
- 默认问题改为向销售顾问询问客户情况，例如“这位客户是什么角色”“客户计划在哪些场景使用这款产品”。
- 提示词明确要求：不得把销售顾问本人误当成客户，禁止询问“您在公司的岗位是什么”这类把销售顾问自身信息当客户画像的问题。
- 允许销售视角措辞，例如“您记录的这位客户在采购中担任什么角色”，但问题对象必须是客户。
- 输入区改名为“客户回答 / 销售观察”，提示优先录入客户原话，转述需注明。
- 对话记录标签改为“销售顾问记录”，避免“客户 / 销售”混称。
- 程序增加自指问题防护：模型若生成“您在公司的岗位/行业/预算……”等把销售顾问当客户的问题，会降级为程序生成客户本位问题。

### 3. 未改变内容

- 仍为每轮一个问题。
- 仍最多 8 轮。
- 仍以 6 个维度覆盖和最多 2 个剩余缺口作为终止条件。
- 未调整证据、预算、决策链或产品匹配的数据契约。

## 二、当前项目基线

当前画像方案的主要特点：

- 使用 DeepSeek 对逐轮销售输入做结构化抽取。
- 每轮只返回一个问题。
- 10 个画像维度，核心维度 6 个。
- 覆盖阈值、缺口阈值和最大轮数由程序独立执行。
- 字段必须有客户原文依据；缺少可定位证据时保持【待确认】。
- 画像完成后可直接带入产品匹配。

当前主要缺口：

1. 有“身份/角色”，但缺少 MEDDIC/BANT 式的经济买家、决策流程、冠军、时间节点、评估指标和竞品状态。
2. 输入来自销售顾问录入，尚未区分“客户直接原话”“销售转述”“模型推断”三种来源。
3. 有 confidence 字段，但界面和规则未形成统一的高/中/低置信度说明。
4. 下一问由缺失维度驱动，没有显式的销售阶段状态（资格确认、需求发现、方案认可、成交推进）。
5. 尚未把画像用于销售演练、异议预演或合成客户仿真。

## 四、详细对比

### 1. zubair-trabzada/ai-sales-team-claude

**优势**

- 将 BANT 与 MEDDIC 落成可执行销售资格流程，覆盖预算、需求、时间、权威、指标、经济买家、决策标准、决策流程、痛点和冠军。
- 把公司研究、决策人识别、机会判断、竞品和外联策略拆成可复用技能，并明确标注证据与置信度。
- 输出不是泛化总结，而是评分、缺口、风险和下一步行动。
- 对销售顾问而非终端客户说话，产品定位与本项目最接近。

**相对当前项目的优势**

- 决策链和资格判断比当前 10 维画像完整。
- 有正式销售框架，不依赖模型临时决定“还缺什么”。
- 有固定的“证据 + 置信度 + 缺口”输出纪律。

**可借鉴**

- 将现有维度映射到 BANT/MEDDIC，但不直接照搬固定权重。
- 增加客户角色、经济买家、决策流程、评估指标、时间节点、冠军和竞品状态。
- 输出“已确认 / 推断 / 未建立”三类资格结论。

**引入成本与风险**

- 成本中等：主要是提示词、字段和页面展示改造；无需引入其 5 Agent 运行框架。
- 仓库主要是 Claude Code Skills 和 Python 辅助脚本，不是可直接嵌入本项目的通用服务。
- 固定评分权重可能不适合华为的政企、教育、渠道和个人消费混合场景。
- 公开网页研究容易把弱信号当成强证据，必须保留本项目现有的人工确认和证据门禁。

### 2. filip-michalsky/SalesGPT

**优势**

- 明确使用 8 个销售对话阶段：介绍、资格确认、价值主张、需求分析、方案呈现、异议处理、成交和结束。
- 阶段分析器每轮只选择“停留”或“进入下一阶段”，与当前逐题推进方式较接近。
- 已有产品知识工具、上下文记忆和多渠道示例，工程成熟度较高。

**相对当前项目的优势**

- 当前只有“维度缺口”，没有“销售阶段”这一层；SalesGPT 能让下一问更符合销售推进节奏。
- 对异议处理和成交推进有明确阶段，而当前画像主要停留在信息采集。

**可借鉴**

- 增加轻量 sales_stage 字段，如：资格确认、需求发现、决策链确认、预算/时间确认。
- 在下一问旁显示当前阶段和本问目的，让销售顾问理解为何问。
- 保持程序控制停止，不让模型无限对话。

**引入成本与风险**

- 最近代码推送为 2024-09-17，距离本次调研已较久，需谨慎看待依赖升级。
- 其产品定位是直接面向潜在客户自动化销售，不是辅助销售顾问做客户画像。
- 直接把销售 Agent 接入可能引入自动外联、承诺和合规风险，不符合当前人工确认边界。
- 建议只借鉴阶段模型，不接入其对话执行链。

### 3. microsoft/TinyTroupe

**优势**

- 微软维护，社区成熟度和持续活跃度最高。
- 支持结构化人格、行为片段、场景仿真、多 Agent 互动和结果验证。
- 示例中包含真实调查结果对照和统计验证，体现了“仿真结果需要校验”的方法。

**相对当前项目的优势**

- 适合在画像完成后做销售演练、异议预演、内容受众测试和方案压力测试。
- 对“人格结构 + 场景 + 行为约束”的表达比单一字段画像更丰富。

**可借鉴**

- 只借鉴其“画像是一个可验证结构，不是一段主观描述”的原则。
- 可在未来增加“基于已确认画像的销售角色演练”，但合成结果必须明确标注为模拟。

**引入成本与风险**

- 成本高：Python 库、模型配置、仿真运行和多 Agent 调用会增加依赖与费用。
- 它主要做**合成人格仿真**，不是从真实销售输入抽取客户事实。
- 若用其合成人格填补真实客户缺口，会违反当前“不补造客户信息”的边界。
- 研究/法律声明要求使用者承担输出责任，不适合作为本轮最小改造。

### 4. msdanyg/buyer-criteria-skill

**优势**

- 明确区分买家话语与销售话语：买家原话是数据，销售发言只能作为上下文。
- 要求逐字证据、说话人和时间戳归属。
- 推断必须单独隔离；资格缺口必须写“未建立”而不是猜测。
- 内置竞品状态检查，未知竞品会作为高价值开放问题处理。

**相对当前项目的优势**

- 当前输入全部来自销售顾问，存在“销售转述被当成客户明确事实”的风险。
- 当前有逐字证据，但缺少来源类型和说话人/时间归属。
- 其“证据不足就写未建立”比当前统一的待确认状态更细。

**可借鉴**

- 增加字段级 source_type：客户直接原话、销售转述、模型推断。
- 销售转述只能进入推断或待核对，不应直接升级为客户明确事实。
- 决策链或竞品信息不足时显示“未建立”，不要用模型常识补齐。

**引入成本与风险**

- 社区规模小，不能把仓库成熟度当作生产保证。
- 仓库以单个 Claude Skill 为主，没有可直接复用的后端 API。
- 当前页面没有通话时间戳，短期内只能复用其证据纪律，不能完整实现其通话审计能力。

## 六、审验结论

- 本轮不直接引入任何第三方代码。
- 不改变已有 8 轮上限、覆盖阈值和画像停止机制。
- 询问措辞已经按销售顾问视角完成小范围修正。
- 是否采用 P1–P5，需要产品负责人确认后再实施。
