# 华销智策 —— 针对华为的销售智能体：协作开发与合并说明

日期：2026年10月20日。目标是让五个模块各自在独立目录、独立Git工作区和功能分支完成实现，验收与联调通过后合并到`main`。

当前交付是协作框架：目录、责任边界、路径检查、分支工作区工具和协作约定。五模块业务逻辑尚未重构，现有线上应用仍使用`backend/marketing/`。本地主分支已建立`main`，原`master`保留；远端默认分支和魔搭部署不因本轮准备自动改变。

## 一、用三个层次实现相对独立

1. **代码独立：**各模块只修改自己的`modules/<模块>/`。源码、提示词、自测、合成样例和内部文档全部包含在该目录，避免不同人争改同一个后端文件。
2. **Git工作区独立：**每个成员有自己的完整仓库工作目录、功能分支和Git暂存区。成员切换分支不会改变别人的文件，成员只在自己的工作区执行Git命令。
3. **接口独立：**模块只接受结构化输入、返回结构化结果。主控负责接线，模块不能直接导入其他模块的内部源码、改其他模块文件或自行启动一套网站。

Git worktree共享提交历史但有独立检出文件，并非操作系统权限隔离。目录权限约定和路径检查需要结合独立QA执行，不宣称能限制任意恶意代码。

## 三、模块交接与并行开发

建议统一`async run(input, context)`入口，由主控注入模型调用、只读资料查询、时钟等公共能力。共同字段与交接草案见`共享规范/接口草案/交接约定.md`；B定版到`contracts/`后再按同一版本实现。

M1和M2可并行开发。M3使用合成的画像和事实包开发，M4使用合成任务书开发，M5使用合成正确稿和错误稿开发，因此不必等全部上游实现后才开工。所有模拟输入都明确标注；最终联调必须替换为真实模块输出。

运行时依次为：客户请求→M1画像→M2证据→M3策略→M4写稿→M5核验。缺失且影响成稿的信息回M1追问；事实或图片问题回M2；切入点不贴合回M3；文风与正文问题回M4；核验程序缺陷回M5。主控限定返修次数，连续失败查因，不能无限重试或降低事实标准。

自然写作验收关注读者、问题、表达节奏、事实与行动引导；不承诺AI检测率，不编造亲测或客户故事。M4不能靠删来源改善文风，M5也不能把所有数字一律拒绝。来源附录与阅读正文分开呈现，但交付时必须同时保留。

## 四、如何启用成员独立工作区

主控先把本轮经过检查的框架文件以明确文件清单提交为`main`上的本地基线；不使用`git add .`。先预览：

```powershell
python tools/team_workspace.py plan
python tools/team_workspace.py create
```

以上两条均只显示计划。基线文件已提交且不存在工作区/分支冲突后，主控执行：

```powershell
python tools/team_workspace.py create --apply
```

工具按`framework/team-layout.json`一次预检全部目标路径、分支和基线文件，再创建五个独立worktree。发现同名路径或分支就停止，不覆盖、不重置；中途失败会报告已创建项并保留现场。不会复制主目录未跟踪的知识库、凭据或模型，也不会联网推送。

成员进入自己的工作区，例如M1：

```powershell
Set-Location 'C:\Users\pop\Desktop\华为项目-模块工作区\M1-customer'
git branch --show-current
```

每个成员看到一份完整仓库，但只写自己的`modules/`子目录；其他模块和公共文件只读。`README`中的目录约定是代码职责，不允许为了方便在别人的目录临时修改。

## 五、成员如何提交，主控如何检查

以M1为例，开发结束后先运行自己的真实测试，再检查受跟踪及未跟踪改动：

```powershell
python tools/team_workspace.py check --member M1 --base main --head HEAD --include-worktree
git diff --check
git add -- modules/customer
git diff --cached --stat
git commit -m "Implement customer understanding module"
python tools/team_workspace.py check --member M1 --base main --head HEAD
```

这些提交命令是后续成员业务完成后的操作示例，不表示已实现客户理解功能。测试命令和实际结果由成员在自己的`docs/`交付说明中提供，不用目录存在替代自测。

路径检查同时识别新增、修改、删除和重命名；跨目录移动时检查旧路径和新路径。越界变更、常见凭据/权重文件会阻止检查通过。它不检查所有语义依赖或保证无密钥，独立QA与发布扫描仍必需。

交付须说明任务ID、模块、功能分支、完整提交ID、公共契约版本、改动文件、输入输出样例、测试命令/结果和已知限制。接口变更只能向B申请，模型适配或界面变更由主控分派原责任人；成员不能通过修改公共文件让自己的测试单方通过。

## 六、任务状态如何保持唯一

根`AGENTS.md`、运行器和Schema已增加M1—M5，原A—E流程继续兼容。正式任务仍由主工作区运行`python -m framework task/send`管理；各成员worktree不创建各自的真实任务看板，以免形成五份互相冲突的状态。

成员把结构化消息交主控转交运行器。Git提交是代码交付，framework的`done`是独立QA验收，两者不可互相替代。QA须在实际候选上核验产出及依赖指纹；上游改变后，受影响下游原任务必须重开复验，不能新增一个任务绕过旧指纹。

## 七、最后如何合并到main

只有主控合并。流程为：

1. 接收模块提交ID，检查分支基线、改动范围、公共契约版本和模块自测证据，独立QA验收该模块。
2. 从最新`main`建立一个本批集成分支，例如`integrate/round-01`。按依赖顺序合入已验收模块；每次合并前记录完整提交ID，使用普通合并，不强推。
3. 冲突停止处理；责任成员解释模块意图，由主控协调原责任人修复，QA复验。共享接口冲突交B处理，不能主控任意选“全部保留本方”。
4. 集成分支进行接口匹配、完整链路、换客户/场景/平台、缺资料、型号冲突和重新生成测试。模块作者通过不替代独立QA。
5. 测试后冻结集成提交ID。若`main`又有变化，先同步并复验；只有`main`仍为该候选祖先且工作区无未提交改动，才允许将验收候选快进合并到`main`。
6. 记录合并前后SHA、模块提交、实际测试及已知限制。业务对外发布时再由E确认同一候选、运行发布门禁与白名单扫描，普通推送和部署后实际验证。

主控在干净的专用集成工作区中可参考：

```powershell
git switch main
git switch -c integrate/round-01
git merge --no-ff feat/customer-understanding
git merge --no-ff feat/evidence-retrieval
git merge --no-ff feat/content-strategy
git merge --no-ff feat/natural-writing
git merge --no-ff feat/quality-delivery
```

以上只是完整一轮的示例；有未完成模块就保留旧适配，不为凑齐五个分支强行合入。真实QA验收完后，回到主控`main`工作区执行`git merge --ff-only integrate/round-01`。集成分支若尚在另一个worktree检出，不在当前worktree强行切换或删除它。公共接口与调用适配也必须进入同一候选测试。

默认使用普通合并保留模块作者和提交记录，禁止覆盖文件夹来代替Git合并；不使用`reset --hard`、强推或删除成员有改动的工作区。回退已合并业务使用新的revert提交并复验，不改写已发布历史。

GitHub当前默认分支仍为`master`，`main`在本地建立不等于远端已有`main`或默认分支已修改。未来首次发布`main`前，须核对GitHub默认分支、魔搭发布脚本目标及已批准候选；这些属于显式发布迁移，不能由成员分支自行操作。

## 八、每个模块合并前的完成条件

- 只有自己的目录发生业务变更，无跨模块源码导入或公共配置偷改。
- 实现正式接口及正常、缺失、冲突、错误返回，自测可独立复现。
- 提供真实结果与明确合成样例；没有把占位、规则或Mock冒称模型成功。
- 来源、型号、价格限制、图片使用条件可追溯；没有凭据或私库入库。
- 独立QA通过；依赖变更已复验；集成候选全链路通过。
- 说明书与实际实现一致；业务发布时再走E签字及发布门禁。

这些是工程合并条件，不是新赛事评分标准。UI美化仍以原评分表达到60分后启动；IMA停用、免费策略及真实报价待核实等约束继续执行。
